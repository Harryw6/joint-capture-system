# Unitree 独立原始流采集设计

日期：2026-09-26。状态：用户已于本设计交付后回复“继续”，批准进入实施计划阶段；尚未实施。

## 1. 用户目标与范围

初始化一次，连续多次开始／停止；相机与手柄保持常驻，机械臂仍须 Home 后使能。采集时优先保留可恢复的数据，避免 PNG／视频编码与在线配对消耗；停止只完成必要落盘和记录收尾。用户自行决定何时导出视频。

本次调整 Unitree 图像保存、对应读取／验收和控制台状态接口，不重构 Go2/Piper/手柄原始 CSV，不改变 P450 格式，不改变遥操速度、Home 门控或对时阈值。旧数据不改写、不删除。

“原始图像”在本方案中指现有 OpenCV 接口交付的 BGR8 像素，不是相机 Bayer 原始信号，也不包含当前未采集的深度／IMU。没有驱动帧号时，不宣称已经证明 USB／传感器层完全无丢帧。

## 2. 证据与取舍

旧流程 CameraReader 仅保留 latest；录制循环要求相机、Go2、Piper、手柄状态同时有效才入队，然后双图 PNG 编码、逐组 PKL 保存。历史测试 2107 组尝试入队，1954 组保存，153 组因队列满丢失。frames_enqueued 当前实际包含入队失败次数，需要纠正定义。skipped_sync_ticks 不是丢帧数，相机 frames 是常驻累计值，也不能直接用于单段完整率。

Unitree 2026-09-26 查询到 4 个在线 CPU、15W 模式、约 15 GiB 内存和 NVMe，磁盘可用约 253 GiB；没有修改电源模式。Python 环境有 LZ4，但尚无 MCAP。

24 组已有 640×480 双相机图像的单线程内存编码测试（不包含磁盘）：

| 方法 | 每组平均处理时间 | 每组平均字节 | 逐像素还原 |
|---|---:|---:|---|
| PNG level 1 | 84.048 ms | 820423 | 一致 |
| PNG level 0 | 35.094 ms | 1847254 | 一致 |
| LZ4 level 0 + checksum | 6.470 ms | 1407361 | 一致 |
| 原始像素复制 | 0.281 ms | 1843200 | 一致 |

选择 MCAP 顺序分块写入 + LZ4 无损压缩，两路独立，不在线配对。PNG0 只适合作为旧格式应急措施，不能解决配对前图像丢弃。无压缩保留为明确配置的降级选项，不能静默切换。暂不迁移 RealSense SDK，避免同时改变相机驱动、常驻机制及时间戳来源；SDK 硬件时间戳属于后续独立工作。

LZ4 样本外推的双路图像空间约 152 GB/小时；无压缩约 199 GB/小时，均不含状态数据。实际压缩率随场景变化，容量保护采用无压缩速率估算。不得将内存编码测量当作持续落盘性能或电池续航实测。

## 3. 数据流与模块边界

1. 常驻 CameraReader：每次成功取帧立即生成接收序号和接收时间，保留原有健康快照；有录制订阅时将本帧不可变的像素所有权交给有界队列，禁止只轮询 latest 来保存。
2. 每路相机单独 FIFO + writer：前置不等待腕部；轻量封装、MCAP 分块 LZ4、顺序写入。图像保存不以机器人状态新鲜度为条件。
3. 状态 CSV：保持现有独立采样与记录。状态缺失要报告，但不丢弃已经到达的图像；启动就绪仍要求两路图像及必需状态均持续写入。
4. CameraSession：控制订阅绑定、分段边界与 writer 生命周期；正常 Stop 不关闭相机或手柄。
5. 离线 reader／validator／converter：统一识别旧 PKL 与新 MCAP，完成完整性检查、时间匹配和按需导出。与采集进程分离。

在 `hetero_pkl_recorder.py` 保留旧格式入口；新 writer/reader 使用独立模块，避免在已有大文件继续混入所有逻辑。`camera_session.py` 与 `collection_manager.py` 仅负责编排和状态，不实现图像编码。

## 4. 格式契约

`meta.json` 增加 `format_version: 2`、`image_storage: mcap`、codec、像素格式、软件版本、配置快照、boot_id。无版本字段按旧 PKL 处理，不能靠“有没有 frames 目录”猜格式。

每段目录保留现有 episode/task 和 raw CSV，增加：

- `raw/cameras/front_000001.mcap`、`wrist_000001.mcap` 等分片。
- 正在写入的文件使用 `.mcap.active` 后缀；完成 footer、flush、fsync 后改名并同步目录。
- `raw/cameras/schema.json`：可读、版本化的像素记录布局说明。
- `capture_manifest.json`：分片、时间覆盖、计数、收尾状态、故障与恢复信息；原子更新。
- 原有 `status.json`、`summary.json`：增加新格式字段和质量信息。

MCAP 消息 payload 使用显式版本的布局：4 字节小端无符号 JSON 元数据长度 + UTF-8 元数据 + 连续 BGR8 像素字节。长度、维度和最大记录大小必须验证；记录不使用 pickle。MCAP Channel 使用明确的自定义 message_encoding `heterovla.raw_image.v1`，schema 使用对应的自定义布局说明，不能伪称 ROS 或 Foxglove 标准图像编码。通用工具能读取容器，显示图像需使用本项目 reader／转换器。

每帧元数据必须包含：camera name/serial、本段序号、常驻 reader 序号、width/height/stride/dtype/pixel_format、接收 monotonic_ns、wall_time_ns、boot_id、timestamp_source=`host_receive`。没有真实设备时间戳时，设备字段为 null，不用主机时间冒充。JSON 内以整数纳秒读写，UI 显示时不能经不安全的 JS 浮点往返写回原值。

MCAP log_time/publish_time 使用主机接收 wall_time；单调时钟随消息保留，离线排序和本机间隔检查以同一 boot_id 内的单调时钟为准。跨机换算使用已保存的对时探测和映射；无有效映射仍允许原始数据读取，但不能标记为已对齐。

每路 MCAP 初始 chunk 目标 4 MiB、分片上限 512 MiB（允许超出最后一条记录的大小），开启 CRC。这些值属于验收前可调整的性能参数，必须记录实际配置。LZ4 不再叠加 PNG 压缩。

## 5. 边界、队列与快速停止

- 每路队列按未压缩字节限制为 64 MiB，总像素排队上限 128 MiB，不按可变帧数无限增长。
- 队列达到 70% 发出积压警告；满队列时不阻塞相机控制线程，也不覆盖旧帧。计数拒收、标记质量失败、触发当前记录任务收尾；不触发机械臂／机器狗运动控制。
- 健康记录要求 received = accepted = written（同一段订阅窗口）；故障下分别报告 rejected/write_errors/pending，不能用一个 frames_saved 代表一组双相机帧。
- Start 以订阅绑定时刻为本段接收边界，不回填上一段 latest。两路实际首帧时间独立记录，共同区间后算。
- Stop 先在短锁内解除两路订阅并固定各路最后接收序号，然后排空本段 writer、写 footer、fsync、保存 summary。不得让下一段帧混入上一段，也不得在持有相机锁时等待磁盘。
- 结束时保留状态源到图像截止点之后，确认 CSV 收尾。等待超时保持 stopping/cleanup_pending 和活动标记，允许幂等重试，禁止提前释放下一段。
- Stop 不做全文件重读、逐像素校验、视频导出或训练 PKL 生成。成功收尾与数据质量通过是两个独立状态；故障数据能结束但必须带不完整标志。
- 相机服务处理 Stop 时仍须能及时响应 status；状态查询不得被最长 55 秒 join 阻塞。

## 6. 持久性、容量与故障

写入线程每约 1 秒将已完成块 flush/fsync，Stop 再同步剩余内容，独立记录 accepted/written/durable 进度。具体 MCAP 版本的块提交方式须在实现前验证，禁止依赖未测试的私有 API。达不到写入或持久化延迟目标时应报错，不能扩大缓冲掩盖。

断电可能丢失队列、尚未提交块及未持久化内容；本设计不承诺断电零丢失或固定“一秒内”。已 fsync 的完整记录为恢复依据，设备缓存等硬件行为仍限制保证。恢复工具只读取损坏源，输出新 recovered 文件与损失区间报告；源文件不覆盖。截断末块、缺少 footer、CRC 错误必须可区分，不能跳过错误后伪称完整。

启动低于 20 GiB 可用空间拒绝记录；运行低于 10 GiB 停止当前记录并排空有限队列，每秒检查。磁盘满、只读、断开或 fsync 失败都必须进入可见故障状态，保留当前文件和恢复信息。开始前显示按未压缩速率估算的剩余分钟，不承诺可录满用户未知时长。

相机拔出／长期无帧、任一路 writer 失败触发采集故障与收尾。联合控制器不得让另一端继续显示“共同采集正常”；接入已有失败收尾逻辑，若无法联系另一端则明确显示停止未确认。手柄控制不由录制故障自动改变。

## 7. 兼容、离线处理与 UI

- 新旧双 reader；更新 `validate_episode.py`、`inspectors.py`、开始就绪检查、summary 解读以及 UI。v2 不要求 `frames/*.pkl` 才认为有数据。
- UI 展示前置／腕部各自接收和保存帧率、队列占用、丢弃／错误计数、写入速率、磁盘剩余时间；显示“原始数据已收尾／质量异常／对时待验收”，不混为一个成功标记。
- 完整验收离线读取全部消息、核验 CRC/尺寸/计数/顺序/各流覆盖和时间戳；没有设备帧号时单独标注“传感器层完整性未验证”。
- 离线转换可输出旧 PNG-in-PKL 或视频。按单调时间为基准确定双相机配对和状态匹配，保留原始时间戳和匹配误差；匹配失败输出报告，不删除原始帧。导出新目录，禁止修改原始文件。
- 只生成满足既有质量阈值的旧格式训练样本；未使能遥操、状态缺口或不可靠时钟映射不能靠补值伪装为有效数据。旧数据中已丢弃的图像无法恢复。
- 数据转移必须同时包含 MCAP、schema、原始状态 CSV、meta/summary/manifest，以及对应本机对时探测与映射文件；单独拷贝图像文件不构成完整训练输入。

## 8. 验收与发布门槛

1. 单元与故障注入：像素逐字节还原，乱序／溢出／磁盘错误可见，Start/Stop 竞态无串段；Stop 超时仍保留所有权；损坏末块不影响已确认可恢复块，CRC 错误不被吞掉。
2. 旧格式回归：既有样本仍可读取／验收，v2 读取失败不能错误回退旧格式，离线转换与时间戳检查有固定小样本。
3. 机器空闲时先做持续写入基准，包含周期 fsync，并记录 p50/p95/p99、吞吐、CPU/RSS。按双路未压缩 55.3 MB/s 加状态流计算，目标至少 2 倍持续吞吐余量；实测不达标不切换默认格式。
4. 实机静止双相机 10 分钟：应用层无拒收／写入错误、计数一致，记录各路帧间隔和有效频率；不能只看平均 FPS。CPU 目标平均低于可用四核总容量 70%，采集队列不得持续增长；阈值是验收目标，不是已测结果。
5. 至少 10 次短分段，保持相机／手柄 PID；正常 Stop 目标 p95 ≤ 3 秒（Unitree 单端，含必要落盘，不含双机网络对时），测试真实慢盘情况下的清晰失败行为。
6. 受控中断仅作用于新建测试记录进程／测试文件，不切断机器人电源，不使能机械臂；实际验证恢复与剩余损失报告。
7. 联合回归：P450 原始 bag 与 Unitree 新数据都能被检查器识别，时钟映射不放宽阈值，视频不自动导出。独立的既有时钟模型异常不得被本次格式升级掩盖。

发布前先备份并验证与现有 Python 3.8、ARM64、LZ4 环境兼容的 MCAP 依赖版本。部署必须在两端无活动采集时进行；生产默认切换仅在上述相关门槛通过后进行。保留旧 recorder 作为显式回滚路径，不在线热换相机所有者。
